## 設計判断（調整できる点）

- builtin ルールは起動時に `rules` へ `source=builtin` で同期する。ファイルが内容の正本で、DB 側は status と hit_count だけ持つ
  （API から builtin の内容変更・削除は 409）。ファイルを消すと行も消える（hit_count も消える）。
- alert の `rule_id` は `sigma:<Sigma id>`、`detector` は登録 id の `sigma`。UI からルールを開くときは `details.rule_ref`（rules 行 id）を使う。
- URI 系フィールドは生値と URL デコード値の両方で照合する（`fieldmap._decoded_variants`）。厳密に「ログそのまま」にしたい場合はここを変える。
- 未知のフィールドや取り込み対象外の logsource は検証エラー（決して発火しないルール、特に LLM の幻覚を弾くため）。Windows 系のコミュニティルールは取り込めない。
- base64 / base64offset は自動で大小文字区別（base64 は大小文字で意味が変わるため）。
- Sigma id が重複するルールの作成・承認は 409（同じ `rule_id` のアラートになり区別できないため）。

## 他モジュールへの依頼

- **intel-advisor**: LLM 提案ルールは `from tokiwa.detect.sigma import validate_rule` →
  `(valid, errors, title)`。合格したものを `RuleRow(kind="sigma", status="proposed", source="llm", title=title,
  meta=rule_meta(parse_rule(content)) | {...})` で保存する。`meta.sigma_id` を入れると API の重複チェックが効く。
  保存後に即反映は不要（proposed は評価されない）。承認は `POST /rules/{id}/approve`。
- **frontend-intel**: `POST /rules/validate` の応答 `{valid, errors[], title?}`、`PATCH /rules/{id}` の本文 `{content?, status?}`、
  `PATCH /detectors/{id}` の本文 `{enabled}`、`POST /rules/reload` の応答 `{active_rules, errors}` はルートモジュール内の
  小さなモデルで、`frontend/src/api/types.ts` には足していない。必要ならインライン型で。
  一覧表示には `Rule.meta`（level, tags, mitre, category, falsepositives, path）が使える。
  422 の `detail` は文字列 `"invalid Sigma rule: e1; e2"`。
- **triage-correlate**: Sigma アラートの `details.falsepositives` を LLM 入力に含めると誤検知判断に効く。
  `ai_score` は `tokiwa.ai_score.NN` タグのあるルールだけで付く（ヒント値）。
- **lab-eval**: ルールの陽性サンプルは `backend/tests/sigma/test_sigma_ruleset.py` の `CASES` にある（シミュレータの参考に）。
- **統合担当**: 新しい定期ジョブ `sigma.flush_hits`（60 秒）と、`detect.sigma.loader` / `api/routes/detectors.py` の `@on_startup` が増えた。
