## 要判断

- #161: 監査の推奨 (a)(b) は「env=prod では起動失敗」。**既定は警告のみ**にし、拒否は `TOKIWA_STRICT_CONFIG=1` の opt-in にした
  （イメージは `TOKIWA_ENV=prod` を焼き込んでおり、`.env` に Compose 用の変数や将来のスクリプト用の変数があると全環境が起動しなくなるため）。
  本番で strict を既定にするかはユーザー判断（`OPERATIONAL_ENV_VARS` に漏れがあると起動不能になる点に注意）。
- #161: 推奨 (c) の「/api/v1/system に設定ソースのハッシュ」は未実施（`api/routes/system` は api レーンの所有。必要なら `config_diagnostics.config_file_status()` を返す）。
- #100: 旧 `?access_token=<JWT>` は**互換のため受け付けたまま**（非推奨 WARNING）。UI は券に移行済みなので、残るのは自作スクリプト・
  アップグレード直後の古いタブだけ。削除（401）にするなら `_stream_user` の `access_token` 分岐を消すだけ。いつ消すかはユーザー判断。
- #100: Caddy の例にはアクセスログのクエリ除外を書いていない（Caddy のログ設定の構文・既定を一次情報で確かめていない）。
- #104: gitleaks（シークレットスキャン）は追加していない — 追加するなら新しいアクション／イメージの SHA・digest を一次情報で取って固定すること。
  GitHub の secret scanning / push protection（リポジトリ設定）でも代替できる。compose の mem_limit / pids_limit は #105/#109 側で扱う。
- #110: tokiwa サーバーには引き続き `.env` 全体が渡る（任意の `TOKIWA_*` を `.env` で設定できる既存の使い方を壊さないため）。
  `.env` に `POSTGRES_PASSWORD` を置く既定の手順も残した。秘密をファイルへ移すのは opt-in（`compose.secrets.example.yaml`）。
  既定を secrets にするなら `.env.example` と make up の手順ごと変える必要がある。
- #71: ラボは volume subpath を使うため **Docker Engine 26 以上**が必要になった（本番 compose の要件 25+ は変えていない）。
- #105 / #109: `mem_limit` / `cpus` は付けていない。低すぎる上限は攻撃中に SIEM / Gate を OOM で落とし、検知が黙って止まる。
  実測なしに値を決められないため、ホストに合わせて運用側で設定する方針（deploy.md §3 に記載）。既定で付けるかはユーザー判断。
- #109: postgres の capability を絞った構成は**起動を確かめていない**（Docker デーモン不可、CI のスモークも postgres プロファイルを
  動かさない）。起動しない報告があれば `cap_drop` / `cap_add` を外すのが最短の回避。CI に postgres プロファイルの起動確認を足すか要判断。

## digest の出所（#104。推測で書いた digest は無い）

（`auth.docker.io/token` / `ghcr.io/token`）で `HEAD https://<registry>/v2/<repo>/manifests/<tag>` を送り、応答ヘッダ
`Docker-Content-Digest` を読む（Accept に OCI index / manifest list を指定）。2026-11-23 に取得し、2026-11-24 に同じ方法で取り直して
リポジトリ内の値と一致することを確認した。actionlint はセッション中に一度だけ実行できた `docker pull` の `Digest:` 表示とも一致。
