# データの取扱い

TOKIWA が **何を受け取り、何を保存し、何を外部へ送り、どれだけ保持し、誰が見られるか** をまとめたページです。
内容は v0.1.0 のコードと既定値に基づきます。コードで確かめられなかったことは「未確認」と書いています。

> ⚠️ **要点（既定値のまま使う場合）**
> - Gate はリクエストボディの先頭 4,096 バイトまで保存します。秘密値・メールアドレス・カード番号は伏字になりますが、
>   **氏名・電話番号・住所・生年月日・ログイン ID などは伏字になりません**。
> - LLM の API キーを設定すると、`medium` 以上のアラートとインシデントが証拠イベントの抜粋とともに
>   **自動で外部の LLM プロバイダへ送られます**。
> - **自動削除は未実装** です。保存したデータは手で消すまで残ります。
> - `viewer` を含むすべてのロールが、ボディを含む生イベントを閲覧できます。
>
> 個人データの取扱いに関する法的な判断は、TOKIWA を導入する組織で行ってください。このページは判断の材料となる事実をまとめたものです。

## 収集と保存

### マスキングはセンサー側で行われる

- Gate と Agent は、イベントをサーバーへ送る **前に、自分のプロセスで** マスキングします。使われる設定は、
  そのプロセスに渡した `llm.redaction.*` です（項目は [LLM の設定とコスト](LLM)）。
- サーバーは受け取ったイベントを **そのまま保存** します（取り込み時に改めてマスクしません）。サーバー側の
  `llm.redaction.*` を変えても、Gate / Agent から届くイベントの保存内容は変わりません。
- 取り込み API（`POST /api/v1/ingest/events`）に自分で送るイベントも、マスクされずに保存されます。送る側でマスクしてください。
- 1 フィールドは `llm.redaction.max_field_chars`（既定 2,048 文字）で切り詰められます（Gate のボディは `gate.capture_body_bytes` まで）。

### センサー別の収集項目

| センサー（dataset） | 保存するもの | 伏字にするもの | 保存しないもの |
|---|---|---|---|
| **Gate**（`gate.http`） | 送信元 / 宛先の IP・ポート、メソッド、Host、パス、クエリ、リクエストヘッダ（先頭 64 個）とその順序、User-Agent、Referer、Content-Type、**テキスト系ボディの先頭 `gate.capture_body_bytes`（既定 4,096）バイト**、ボディのサイズ、ステータス、応答のサイズと Content-Type、処理時間 | `llm.redaction.sensitive_headers` のヘッダ値（`Authorization`・`Cookie` など）と、下の「伏字になるもの」 | 応答の本文、応答ヘッダ（Content-Type 以外）、バイナリのボディ（サイズだけ記録）、65 個目以降のヘッダ |
| **Gate のデコイ配信**（`gate.deception`） | 上と同じ HTTP の内容をもう 1 件（デコイのログインフォームに入力された値も含む） | 同上 | 同上（このリクエストは守りたいアプリへ転送されない） |
| **nginx / Caddy**（`nginx.access` / `caddy.access`） | 送信元 IP・ポート、メソッド、Host、パス、クエリ、ログに含まれるヘッダ、ステータス、サイズ、処理時間、元のログ行（`raw`。伏字の後、4 KB まで） | ヘッダ値（同上）、`password`・`token`・`cookie` などのキーの値、下の「伏字になるもの」 | リクエストボディ（アクセスログには含まれない） |
| **Zeek**（`zeek.conn` / `zeek.http` / `zeek.notice`） | 接続（IP・ポート・バイト数・状態）、HTTP（パス・クエリ・UA・Referer・ステータス）、notice、元の行（`raw`、4 KB まで） | `password` などのキーの値、下の「伏字になるもの」 | 上の 3 種類以外のログ。なお `http.log` の **`username` 列は伏字の対象外** で、`raw` にそのまま残る |
| **Suricata**（`suricata.eve`） | `alert` / `http` / `flow` / `dns` のレコード（IP・ポート、HTTP のパス・クエリ・ヘッダ、DNS の問い合わせ名と応答）、元の EVE レコード（`raw`、4 KB まで） | ヘッダ値、キー名による伏字、下の「伏字になるもの」 | `tls`・`fileinfo`・`stats` などの他の種類。EVE にペイロードを出力する設定の場合、その内容は `raw` に 4 KB の範囲で入りうる |
| **ホストセンサー**（`host.ports` / `host.connections`） | ホスト名・ホストの IP（最大 32 個）・OS、待ち受けソケット、新しい TCP 接続（双方の IP・ポート）、そのプロセスの名前・実行ファイル・コマンドライン（512 文字まで）・OS のユーザー名 | コマンドライン中の `password=...` 形式の値など | — （引数として渡したパスワードは伏字にならないことがある） |
| **取り込み API**（直接送信） | 送られたイベントのすべて | **なし**（サーバーではマスクしない） | — |
| **デセプションのトリップ記録** | 触れた資産、送信元 IP、イベント ID、パス、メソッド、UA、罠の値（TOKIWA が生成した偽の値）と、それが現れたフィールド名 | — | — （資産を削除してもトリップ記録は残る） |

### 伏字になるもの・ならないもの

マスクされた値は `[REDACTED:<種類>]` に置き換わります。

| 伏字になる | 伏字にならない（例） |
|---|---|
| 秘密鍵、JWT、主要サービスの API キー・トークンの形式（Anthropic・OpenAI・AWS・GitHub・Slack・Google）、`Bearer` / `Basic` 認証の値 | 氏名、電話番号、住所、生年月日 |
| `password=`・`token=`・`secret=`・`api_key=`・`auth=`・`session=` などに続く 3 文字以上の値 | ログイン ID（`username=` などの値）、2 文字以下のパスワード |
| URL に埋め込んだ認証情報（`https://user:pass@...`） | URL エンコードされたメールアドレス（`%40` を含むもの） |
| Luhn 検査を通るカード番号 | IPv6 アドレス（`mask_ips` は IPv4 だけが対象） |
| メールアドレス（`mask_emails`、既定 ON） | イベントの送信元 / 宛先 IP の欄（`mask_ips` を ON にしても対象外） |
| 文字列中の IPv4 アドレス（`mask_ips`、既定 OFF） | |

### サーバー内で複製される場所

同じ個人データが、検知とトリアージの過程で複数のテーブルに写ります。削除や開示の対応では、次のすべてを確認する必要があります。

| テーブル | 個人データが入りうる項目 |
|---|---|
| `events` | イベント全体（上の表の内容。`raw` を含む） |
| `alerts` | 送信元 IP、タイトル、`entities`（パス・Host・パラメータ名）、`details` の一致箇所の断片（Web 系の検知で最大 200 文字）、トリアージ結果 |
| `incidents` | 送信元 IP の一覧、LLM が書いた要約（最大 4,000 文字）、トリアージ結果 |
| `actor_sessions` | 送信元 IP、User-Agent、振る舞いの特徴量 |
| `llm_calls` | LLM に渡した入力（マスク済み、最大 100,000 文字）と応答。プロバイダが `mock` でも記録される |
| `copilot_messages` | コパイロットとの会話と、ツールの結果（イベントのボディ先頭 300 文字などを含む） |
| `deception_trips` | 上の表のトリップ記録 |
| `response_actions` | 対処の対象 IP、理由（LLM が書いた文を含む） |
| `audit_log` | 操作したユーザー名、対象、詳細 |
| `users` | TOKIWA の利用者名、パスワードのハッシュ、最終ログイン時刻 |
| `notification_channels` | 通知先のメールアドレス、SMTP のユーザー名、Webhook の URL |
| `settings_kv` | 画面から入力した LLM の API キー（平文） |

### 収集を減らす

```bash
# Gate のプロセスに渡す
export TOKIWA_GATE__CAPTURE_BODY_BYTES=0   # ボディを保存しない（サイズだけ記録）。--capture-body-bytes 0 と同じ
# 値を丸ごと伏せるヘッダを追加する（既定の 7 個も並べ直すこと）
export TOKIWA_LLM__REDACTION__SENSITIVE_HEADERS='["authorization","cookie","set-cookie","proxy-authorization","x-api-key","x-auth-token","x-csrf-token","x-forwarded-user"]'

# Agent のプロセスに渡す
export TOKIWA_AGENT__CONNECTIONS=false     # 新しい TCP 接続を送らない
export TOKIWA_AGENT__HOST_SENSOR=false     # 待ち受けポートとプロセスの情報を送らない
```

- `sensitive_headers` に `deception.canary_header`（既定 `X-Debug-Auth`）を入れると、AI カナリアを検知できなくなります。
- nginx の `log_format` には Cookie・Authorization・リクエストボディを入れないでください（`lab/nginx/tokiwa-json.conf` の注記）。
- `mask_ips` を ON にすると、検知や対処の提案に影響しうるため、試験環境で確かめてから使ってください（影響の範囲は未確認）。
- Gate の `--access-log`（既定 OFF）を付けると、uvicorn の標準のアクセスログ（クライアントのアドレスとリクエスト行）が標準出力に出ます。このログは TOKIWA のマスキングを通りません。

## 外部への送信

### 送信先の一覧

| 送信先 | いつ | 何が送られるか | 止め方 |
|---|---|---|---|
| LLM プロバイダ: 自動トリアージ | `triage.min_severity_for_llm`（既定 `medium`）以上のアラートの作成時。インシデントの作成時と、重大度・攻撃段階などが変わったとき | アラート / インシデントの内容（タイトル・説明・送信元 IP・entities）、証拠イベント最大 `triage.max_evidence_events`（既定 25）件の抜粋、AI セッションの特徴量、関連する脆弱性 | `triage.auto_triage=false`、または外部のプロバイダを使わない（下記） |
| LLM: 手動トリアージ | `analyst` 以上が画面や API から実行したとき（`auto_triage` と最低重大度に関係なく実行される） | 同上 | 外部のプロバイダを使わない |
| LLM: コパイロット | 利用者が質問したとき | 質問、会話の履歴、参照専用ツールの結果（イベントのパス・クエリ・UA・ボディ先頭 300 文字、アラート、インシデント、資産など） | `copilot.enabled=false` |
| LLM: 脆弱性アドバイザリ | 資産に一致する脆弱性が見つかったときと、定期実行 | 脆弱性の情報、一致した資産の名前・種類・重要度・ソフトウェア | `intel.enabled=false` |
| LLM: Web リサーチ | `intel.research_interval_hours`（既定 12）時間ごと。プロバイダが `mock` 以外のときだけ | 調査テーマ、資産のソフトウェア一覧（ベンダー・製品・バージョン）。検索はプロバイダ側で行われる | `intel.research_enabled=false` |
| 通知チャネル（Webhook / Slack / Discord / メール） | アラート・インシデントの作成、インシデントの重大度の上昇、対処の提案 | 下の「通知に載る内容」 | チャネルの無効化・削除、`notify.default_webhook_url` を外す、`notify.notify_action_proposals=false` |
| 対処の `webhook` / `notify` | その対処が承認されたときだけ | 対処の ID・種類・対象 IP・TTL・インシデント / アラートの ID | 承認しない。`response.webhook_urls` を設定しない |
| 脆弱性フィード | `intel.sync_interval_minutes`（既定 360）分ごと | **問い合わせだけ**: 期間（NVD・JVN・GHSA）、CVE ID（EPSS）、資産のソフトウェアのエコシステム・パッケージ名・バージョン（OSV）。テレメトリは送らない | `intel.enabled=false`、または `intel.sources.<名前>=false` |

### LLM に送られる証拠の中身

トリアージでは、各証拠イベントから次の項目だけを抜き出して送ります。元のログ行（`raw`）は送りません。

- ID・時刻・種類、送信元 / 宛先の IP とポート、ホスト名、セッション ID、タグ
- HTTP: メソッド・Host・パス・クエリ・ステータス・サイズ・Content-Type、一部のヘッダ（User-Agent・Referer・Origin・
  Accept 系・`X-Forwarded-For` など 13 種）とヘッダの順序、**ボディの先頭 512 文字**
- HTTP 以外: `raw`・ラベルなどを除いたイベントの内容（ホストセンサーのコマンドラインなどを含む）

送る直前に、サーバーの `llm.redaction.*` でもう一度マスクし、「信頼できないデータ」の囲みに入れます。
プロバイダ側での保存期間や利用の条件は、各プロバイダの規約によります（TOKIWA からは制御できません。内容は未確認）。

### 外部の LLM に送らないようにする

```bash
# サーバーに渡す
export TOKIWA_LLM__PROVIDER=mock               # 外部へ送らない（LLM の判定はモックとルールベースになる）
export TOKIWA_TRIAGE__AUTO_TRIAGE=false        # 自動トリアージ自体をしない（llm_calls への記録も減る）
export TOKIWA_COPILOT__ENABLED=false           # コパイロットを止める
```

- **画面の設定が環境変数より優先されます**。**LLM → 設定** でプロバイダを保存していると、環境変数で `mock` にしても
  そちらが使われます。**LLM → 設定** の「現在の状態」で、実際に使われているプロバイダを確認してください。
  マスキング（`llm.redaction.*`）は画面からは変えられません。
- `mock` でもトリアージは動き、入力は `llm_calls` に保存されます（外部へは送られません）。予算超過で送らなかった呼び出しも、
  入力は記録されます。
- 自組織内で動かす OpenAI 互換のサーバー（`llm.provider=openai_compat`）を使うと、送信先を自組織内に限れます（[LLM の設定とコスト](LLM)）。
- サーバーで `mask_ips=true` にすると、LLM が対処の対象 IP を示せなくなり、LLM からの遮断などの提案が作られなくなる見込みです
  （コードからの推定で、動作は未確認）。

### 通知に載る内容

| 通知 | 載る内容 |
|---|---|
| アラート | タイトル（最大 200 文字）、説明（最大 600 文字）、送信元 IP、カテゴリ、ルール ID、AI スコア |
| インシデント | タイトル、送信元 IP（本文に 5 件、Webhook の `data` に 20 件まで）、アクターの種類、AI スコア、アラート数、攻撃段階、**要約（最大 600 文字）** |
| 対処の承認依頼 | 対処の種類、対象 IP、TTL、提案元、**理由（最大 500 文字）** |

- イベントのボディ・クエリ・ヘッダは載せません。ただし、アラートのタイトルや説明には、パスやパラメータ名など攻撃者が制御できる文字列の一部が入ることがあります。
- インシデントの要約と対処の理由は、LLM がトリアージで書いた文になることがあります。LLM が証拠中の個人項目を書いた場合、その文がそのまま通知先へ送られます（実際の LLM でどの程度起きるかは未確認）。
- 通知に載せる項目を選ぶ設定はありません。

## 保持期間

<!-- TODO(integrator): #158 の統合後に更新 -->

- **自動削除（保持期間の設定・パージ）は未実装です**。イベント・アラート・インシデント・LLM の呼び出し記録などは、
  手で消すまで無期限に残ります（[#80](https://github.com/JUCK-Kurohasu/TOKIWA/issues/80)、
  [#158](https://github.com/JUCK-Kurohasu/TOKIWA/issues/158)、[#171](https://github.com/JUCK-Kurohasu/TOKIWA/issues/171)）。
- 画面や API から削除できるのは、ユーザー・API トークン・ルール・資産・デセプション資産・コパイロットの会話・ポートの
  ベースライン・通知チャネルだけです。イベント・アラート・インシデント・AI セッション・LLM の呼び出し記録・監査ログを消す機能はありません。
- コパイロットの会話を削除しても、その会話で行った LLM 呼び出しの記録（`llm_calls`）は残ります。デセプション資産を削除しても、トリップ記録は残ります。
- Gate と Agent は、サーバーへ送れない間イベントを **メモリ上** に溜めます（Gate は既定 10,000 件、Agent は 50,000 件まで。ディスクには書きません）。
- データは `database.url` の DB（既定 `./data/tokiwa.db`）に入ります。TOKIWA は DB ファイルの権限を設定しません
  （OS の umask に従います。ログイン用の署名鍵 `secret.key` だけは 0600 で作ります）。DB のバックアップにも同じデータが含まれます。

### ロール別（API の権限）

[Web UI ガイド](Web-UI) のロール表は「できる操作」の区分です。閲覧できるデータは、API の権限で次のように決まっています
（画面に表示されない項目も、API では取得できます）。

| データ | `viewer` | `analyst` | `admin` |
|---|:-:|:-:|:-:|
| 生イベント（ボディ・クエリ・ヘッダ・`raw`、ホストのプロセスのコマンドラインと OS ユーザー名を含む） | ✅ | ✅ | ✅ |
| AI セッション（送信元 IP・User-Agent） | ✅ | ✅ | ✅ |
| アラート（`details` の一致箇所を含む）、インシデント（要約・トリアージ結果） | ✅ | ✅ | ✅ |
| デセプションのトリップ記録、対処の一覧（対象 IP・理由） | ✅ | ✅ | ✅ |
| LLM 呼び出しの一覧（用途・費用・状態。入力と応答の本文は含まない） | ✅ | ✅ | ✅ |
| コパイロットの利用（ツールでイベントなどを検索できる） | ✅ | ✅ | ✅ |
| LLM 呼び出しの入力と応答の本文 | — | — | ✅ |
| 他の利用者のコパイロットの会話 | — | — | ✅ |
| 監査ログ、ユーザー一覧、通知チャネルの設定 | — | — | ✅ |

- リアルタイム配信（`GET /api/v1/stream`）は、ログインしている全員に、アラート（`details` を含む）・インシデント・対処の内容と、
  デセプションのトリップ（送信元 IP）を送ります。イベントは件数だけで、LLM 呼び出しの入力と応答は送りません。
- **閲覧の記録は残りません**。監査ログに残るのは変更操作だけで、イベントの閲覧・検索、コパイロットの利用、ログインの成功は記録されません。

### TOKIWA の外で見られる人

- DB ファイルとそのバックアップを読める人（OS の利用者、バックアップの管理者）
- LLM プロバイダ（送った範囲）
- 通知先のサービス（Slack・Discord・メールサーバー・Webhook の受信側）と、そのチャネルの参加者
- Gate / Agent が動くホストの管理者（送信前のイベントがメモリ上にある間）

## 本人からの求めへの対応

<!-- TODO(integrator): #158 の統合後に更新 -->

特定の人（IP アドレス・ログイン ID など）に関するデータを **まとめて検索・書き出し・削除する機能はありません**。

- **探す**: イベントは送信元 IP（`GET /api/v1/events?source_ip=...`）や、パス・User-Agent の部分一致（`q=`）で絞り込めます。
  ボディやクエリの中身で検索する API はありません。
- **書き出す・消す**: DB を直接操作するしかありません。上の「サーバー内で複製される場所」のテーブルをすべて確認してください。
  特に `llm_calls` の入力には、同じ証拠がアラートとインシデントのトリアージで繰り返し写ります。
  DB を直接編集する前に、サーバーを止めてバックアップを取ってください。
- **外部へ送ったもの**: LLM プロバイダや通知先へ送った内容は、TOKIWA からは取り消せません。

## 運用者が確認すべき論点

どの法令や規程が適用され、何が必要になるかの判断は、TOKIWA を導入する組織の責任で、必要に応じて専門家と確認してください。
次は一般的な論点の一覧で、網羅的なものではありません。

- **利用目的**: 守りたいアプリの利用者のデータ（フォームの入力・IP アドレスなど）をセキュリティ監視に使うことを、特定・通知・公表する必要があるか。
- **収集の最小化**: ボディの保存（`gate.capture_body_bytes`）は必要か。ログの形式やヘッダに不要な項目がないか。
- **外部への提供**: LLM プロバイダや通知先サービスへの送信が、委託・第三者への提供・国外への移転のどれに当たるか。提供先での保存期間と二次利用の条件。
- **保存期間**: 何日残すか。自動削除がないので、削除の手順と担当者を決める。
- **アクセス権**: 誰に `viewer` 以上の権限を渡すか。閲覧の記録が残らないことを前提にした管理。
- **安全管理**: DB ファイルとバックアップの権限・暗号化。画面から入れた API キーが平文で DB に保存されること。
- **本人からの請求**: 開示・訂正・削除・利用停止などを求められたときの手順と期限。
- **漏えいしたとき**: どのテーブル・どの外部の送信先にデータがあるかを、このページを基に把握しておく。
- **従業員の監視**: ホストセンサーや Gate が従業員の通信・操作を記録する場合の社内規程と周知。
- **デセプション**: デコイや AI カナリアの文言と配置（[デセプション（Mirage）](Deception)）。
