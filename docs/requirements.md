## 0. v0.1 からの主な変更

- 名称を「LLM支援型SIEM（仮称）」→ **TOKIWA** に確定。ARTEX（AI 自律ペンテスト）と対をなす防御側として位置づけ。
- 主眼を「**生成AI / LLM エージェントによる攻撃の検知・防御**」に明確化（FR-13〜15）。
- XDR 化: リバースプロキシ型センサー **TOKIWA Gate** でボディを含む捕捉と即時の遮断・誘導（FR-16）。
  v0.1 §8 の「アクセスログだけではボディが見えない」課題への回答。
- 能動的防御: デセプション（Mirage, FR-17）。
- 脆弱性インテリジェンス: フィード（KEV/EPSS/NVD/OSV/JVN/GHSA/RSS）+ LLM の定期 Web リサーチ（0day 監視）+ 資産照合 +
  LLM 助言・Sigma ルール提案（FR-08 拡張, FR-18）。
- Web ダッシュボードと SOC コパイロット（FR-10 拡張, FR-19）。
- 未決事項の多くを ADR で決定（スタック・ストア・スキーマ・LLM・ライセンス暫定）。

## 1. 目的と背景

- 目的: ポート・HTTP リクエスト・LLM アプリへの入力・脆弱性情報を監視し、ルール + 振る舞い分析で検知、
  LLM で根拠付きにトリアージし、可逆な対処を人間の承認のもとで実行する防御基盤を **実際に動かす**。
- 背景: LLM エージェントを使った攻撃ツール（自律ペンテスト、ARTEX 等）の台頭。偵察〜試行の速度と適応性が上がり、
  脆弱性の公表から悪用までが短期化。人手の一次トリアージだけでは追いつかない。
- 成功の定義（M3 時点）: ラボで AI エージェント型・スキャナ型・人間型の攻撃と正常利用を区別して検知し、
  LLM が根拠付きで優先度を付け、評価セットで指標（検知率・誤検知率・AI 判定精度・コスト）を出せる。

## 2. スコープ

| 区分 | 内容 |
|---|---|
| 対象 | 自分が管理する Linux ホスト / ラボ、Gate またはリバースプロキシ経由の HTTP(S)、リスニングポートと接続、保護対象の LLM アプリ、資産に関係する脆弱性情報 |
| 対象外（当面） | Windows エンドポイント、EDR 相当のプロセス/ファイル監視、TLS の MITM 復号（Gate は TLS 終端の内側に置く）、フル PCAP 長期保存、独自 ML モデルの学習、反撃（hack-back） |
| 前提 | 監視対象は自分の管理下のみ。勤務先のログ・コード・機密を持ち込まない |

## 4. 非機能要件

| 区分 | 要件 |
|---|---|
| 安全性 | テレメトリは常に非信頼データ。LLM 出力をコマンド・クエリ・設定変更に直結させない。ツールは参照系のみ。対処は許可リスト型・検証済みパラメータ・既定で人間承認 |
| 秘匿 | 送信前マスキング（ヘッダ秘匿リスト、トークン/鍵/メール/カード番号）。Gate でも送信前に適用。ローカル LLM 選択肢 |
| コスト | 日次予算、呼び出し単位の入力上限、ティア分け、プロンプトキャッシュ、重大度しきい値未満は LLM に送らない |
| 監査性 | LLM 入出力・モデル・プロンプト版・トークン・費用を記録。承認・設定変更を監査ログに記録 |
| 再現性 | Docker Compose でラボ一式を再現。シミュレータは乱数シード固定 |
| 差し替え可能性 | センサー・検知器・ストア・LLM プロバイダ・インテル取得元・通知チャネルをインタフェースで分離（自動登録） |
| 可用性 | Gate はサーバー停止時に fail-open（遮断ポリシーは最後に取得したものを保持） |
| 性能 | ラボ目標: 取り込み 300 events/s、Gate 300 RPS、取り込み→アラート < 1s、トリアージ < 30s（fast）。計測後に見直し |

## 6. LLM 設計方針

v0.1 §7 を継承し、以下を追加:
- 7. 拒否（refusal）・予算超過・不正出力は正常系として扱い、ルール判定へフォールバック。
- 8. AI アトリビューションの最終判断は LLM 単独に依存しない（振る舞いスコア + デコイ証拠 + LLM 判定の合議）。
- 9. Web リサーチは信頼ドメインの許可リストで行い、出典 URL を必ず保存。リサーチ結果の CVE はフィードで裏取りされる
   まで「research 由来（未確認）」として扱う。

## 7. フェーズ（マイルストーン）

| M | 内容 | 受け入れ基準 |
|---|---|---|
| M0 基盤 | 骨格・契約・CLAUDE.md/AGENTS.md/HANDOFF.md・CI | `uv run pytest` 緑、`tokiwa serve` で UI が出る |
| M1 検知 | ポート監視・Web 署名・Sigma・Gate 捕捉・AI 振る舞い検知 | 許可外リスナー起動でアラート。ラボ攻撃でルール発火、正常トラフィックの誤検知が基準以下 |
| M2 判断 | 相関・LLM トリアージ・インテル・デセプション・対処ワークフロー | KEV 該当 CVE 関連が上位。承認なしで対処が実行されないことをテストで保証 |
| M3 評価 | ラボ + シミュレータ + 評価ハーネス + ARTEX 演習 | 評価セットで検知率・誤検知率・AI 判定精度・コストを算出、回帰比較できる |
| M4 運用 | Alembic、PostgreSQL 運用、性能チューニング、公開準備 | ライセンス確定、README/ドキュメント整備 |

評価指標: 検知率、誤検知率、AI アトリビューションの precision/recall、LLM 判定とラベルの一致率、
1 アラートあたりトークン/費用、取り込み→トリアージ遅延。

## 8. 設計上の注意（見えるもの / 見えないもの）

- アクセスログのみではボディが見えない → Gate を推奨構成とする。Gate を置けない場合はボディ依存攻撃
  （デシリアライズ系 RCE、RSC/Server Actions 悪用など）の検知力が落ちることを UI/ドキュメントで明示。
- HTTPS は TLS 終端の内側（Gate を終端プロキシの後ろ、またはアプリの前段）に置く。
- ホスト視点（誰が listen）と NW 視点（誰が叩く）は別物。FR-01/02 はホスト、FR-03 は NW/HTTP。
- NAT/VPN/共有 IP ではセッション分割が粗くなる（AI 判定の限界として明記）。

## 9. リスク

| リスク | 対策 |
|---|---|
| ログ経由のプロンプトインジェクション | 非信頼データ封入、出力スキーマ固定、参照系ツールのみ、実行系非接続 |
| AI 判定の誤り・回避 | 説明可能スコア、デコイによる決定的証拠、評価セットでの継続検証、断定表現の抑制 |
| コスト膨張 | 事前フィルタ、ティア分け、日次予算、キャッシュ |
| 誤遮断 | 既定で人間承認、TTL、保護 CIDR、取り消し、fail-open |
| ログ内の個人情報・秘密 | マスキング、保持期間（TODO: 保持期間設定とパージジョブ） |
| デセプションの法的・倫理的問題 | 自組織資産のみ、偽データのみ、反撃なし（docs/deception.md） |
| スコープ拡大 | マイルストーンの受け入れ基準で線引き、タスク仕様で担当範囲を限定 |
