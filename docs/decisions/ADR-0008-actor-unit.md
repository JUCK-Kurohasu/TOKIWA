# ADR-0008: アクターを数える単位（IP + UA からの移行）

- 状態: **提案**（2026-11-28。決定はユーザー）
- 関係する Issue: #18 #73 #24（high）、#46 #47 #49 #114 #142 #74 #117 #61（従属）
- 関係する文書: ADR-0006（アクターセッション単位の特徴量）、`tokiwa.aidetect.sessions` / `fingerprints`

## 背景（事実）

- アクターセッションのキーは `source_ip` + `client_fingerprint` で、後者は UA の値と安定したヘッダ名の集合のハッシュ
  （`tokiwa.aidetect.fingerprints`）。セッションは event time で `detection.session_idle_timeout_seconds`（既定 1800 秒）続く。上限は
  `detection.max_live_sessions`（既定 4096、LRU）。
- その下流もすべて IP 単位で動いている。Web 検知のアラート重複排除キー（`<rule>|<source_ip>|<path_key>`、`tokiwa.detect.web_common`）、相関キー `ip:`、対処提案の対象（/32・/128）、
  Gate のレート制限バケットがそうである。
- 監査で確認された崩れ方は次のとおり。
  - **分断**: 要求ごとに UA を替える（Nuclei の既定動作）とセッションが 1〜2 件ずつに割れ、AI 判定も振る舞い検知も
    成立しない（#18）。IP を回す場合も同様（#46）。
  - **増殖**: 回すたびにアラート・インシデント・提案が増え、6300 リクエストから提案約 2100 件が生まれた（#73 #24）。
  - **合流**: NAT 配下で同じ UA の正規利用者が 1 セッションに混ざり、AI と誤判定される（#49）。
  - **低速**: 30 分を超える間隔では全要求が単発セッションになる（#47）。
- 本 PR（#22）で、送信元 IP は信頼プロキシ経由でしか詐称できなくなった。ただし実際に IP を回せる攻撃者
  （クラウド・住宅プロキシ・IPv6 /64）には効かない。

## 選択肢

| 案 | 内容 | 効く穴 | 代償・リスク |
|---|---|---|---|
| A. キーから UA を外す | セッションキーを `IP + 安定ヘッダ名集合`（UA の値を除く）にし、UA は特徴量に回す | #18（UA 回転） | 同じ IP の別クライアントが合流しやすくなる（#49 が悪化） |
| B. キーをネットワーク接頭辞にする | `/24`（v4）・`/64`（v6）単位で集約する | #46 の一部・#142 | NAT・共有 IP で大量に合流する。#23 の共有アドレス問題を検知側に持ち込む |
| C. 2 層化（セッション + キャンペーン） | セッションは現状に近いまま残し、その上に「キャンペーン」層を置く。同じ標的への同じペイロード系統・同じパス列・時間的に近いセッションを、接頭辞（/24・/64）と ASN を弱い手掛かりにして束ねる。アラートの重複排除・インシデント・対処提案はキャンペーン単位で行う | #73 #24 #142 #74 #117 #61（増殖側）、#18 #46 の判定側（キャンペーン単位で AI 特徴を再計算） | 実装量が最大。束ね方の誤り（無関係なアクターの合流）が提案に波及する。評価データが要る（#174 #127） |
| D. 指紋の強化 | TLS（JA4）・HTTP/2 フレーム順・ヘッダ順でクライアントを識別する | 分断・合流の両方 | Gate が TLS 終端していない構成では取れない（#28）。今のイベントにない |

## 推奨

**C を目標とし、A を先行させる**。B は単独では採らず C の手掛かりの 1 つとし、D は #28 と合わせて別途検討する。

1. **A（先行・小）**: `client_fingerprint` から UA の値を外し、UA は「宣言されたクライアント種別」の特徴量に回す。
   #18 の分断を止める最小の変更である。#49 の悪化は、合流を示す特徴量（同一セッション内の UA 種類数・Accept-Language の種類数）を
   スコアに入れて相殺する。**評価セットで AI 再現率と正常セッションの誤判定率を前後比較してから入れる。**
2. **C（本体）**: `tokiwa.correlate` に `campaign_id` を足す（events / alerts / incidents に nullable 列）。対処提案は、
   キャンペーン内の送信元を `ipaddress.collapse_addresses` で束ねた CIDR 1 件にまとめる。安全側の上限は既存の
   `min_prefix_v4/v6` と、本 PR の `shared_cidrs` を使う。アラートの重複排除キーは `rule|campaign|route` にする。
3. **Gate**: レート制限のバケットを `/64`（v6）に寄せる（#142）。これは C を待たずに入れられる。

## 未確定・要検証

- キャンペーンを束ねる条件（時間窓・類似度の閾値）は仮説。#174 の評価スイートは現状天井に張り付いているため、
  先に IP・UA 回転のプロファイルを足す（#127）必要がある。
- 束ね誤りによるフレーミング（無関係な正規 IP がキャンペーンに入り CIDR 提案に含まれる）を防ぐため、
  CIDR 提案は自動承認しないことを C の前提にする。
- 実物の AI 攻撃ツールでの検証はしていない（監査と同じ制約）。
