# ADR-0007: 秘匿化・切り詰めと検知の順序（検知の入力を攻撃者に消させない）

- 状態: **提案**（2026-11-28。決定はユーザー）
- 関係する Issue: #20 #21 #31 #29 #36 #159 #156（従属）、#140 #141（第 3 弾で部分解決）
- 関係する文書: docs/tasks/gate.md §1（「送信前に `tokiwa.llm.redact`」）、ADR-0003（イベントスキーマ）

## 背景（事実）

- Gate はイベントを**作る時点で**秘匿化する（`tokiwa.gate.capture` → `tokiwa.llm.redact`）。サーバーに届くのは伏字済みの値で、
  Web 検知器はすべてサーバー側でそれを見る。Gate 自身は検知器を走らせない。
- `secret_param` パターンは「`token` / `auth` / `session` などのキー名 + `=` か `:`」の後ろの値を、内容に関係なく伏字にする。
  値の先頭に `token:` を書くだけで後続のペイロードが `[REDACTED:...]` になり、署名検知を全部回避できる（#20、再現済み）。
- 長さの上限は `llm.redaction.max_field_chars`（2048）と `gate.capture_body_bytes`（4096）。前方パディングでペイロードを
  上限の外へ押し出せる（#21）。サーバー側のイベント上限（65,536 文字、第 1 弾）はこの穴を広げないように決めた値で、穴自体は残っている。
- `cookie` / `x-api-key` / `x-auth-token` などはヘッダ名だけで値ごと伏字になる（#31）。そのため Cookie 経由の SQLi・
  デシリアライズ・Log4Shell は見えない。ハニートークンの「自然な使い方」も同じ理由で消える（#29）。
- 一方で、秘匿化には根拠がある。秘密情報を DB・LLM・ログに書かない（AGENTS.md §2-5）ことと、Gate→サーバー間の通信路が
  平文になりうる（#139: CA 指定手段がなく、http:// で繋ぐ構成がある）ことである。

問題の根は「**消すか残すか**を値の中身を見ずに決めていて、消したことが検知に伝わらない」点にある。

## 選択肢

| 案 | 内容 | 塞がる穴 | 代償・リスク |
|---|---|---|---|
| A. 現状維持 + 文書化 | 限界を docs に書く | なし | #20 #21 の high 2 件が残る |
| B. 値の形で伏字を判断 | `secret_param` などの値ベースのパターンは、値が秘密らしい形（英数・記号の一部・一定のエントロピー）のときだけ伏字にする。クォート・空白・`(`・`<`・`${` などを含む値は「攻撃文字列の可能性」として残す | #20 の大半 | 記号を含む本物のパスワードが平文で残りうる。境界の調整が要る |
| C. Gate で粗い検知シグナルを付ける | 伏字・切り詰めの**前**の生値に対して、Gate が軽量な形状検査（SQL・シェル・テンプレートのメタ文字クラス、ネストしたエンコード段数、JNDI 形）を走らせ、`gate.masked_signals=sqli,jndi` のようなラベルを付ける。サーバーは「伏字 + シグナル」を検知の根拠にする | #20 #21 #31 #29 の検知漏れ（中身は見えないが「何かあった」は残る） | Gate の CPU。判定ロジックが Gate とサーバーの 2 か所に分かれる（版ずれ）。シグナル名は Gate を信頼する前提 |
| D. 検知してから秘匿化 | Gate は生値を送り、サーバーが検知を済ませてから伏字にして保存・LLM 送信する | 最も広い（#20 #21 #31 #29 #36 の検知側） | 秘密が通信路とサーバーメモリを通る。**#139（TLS 検証）が前提**。docs/tasks/gate.md の約束が変わる。サーバー側の上限・メモリ設計の見直し |

## 推奨

**C を先に入れ、B は C の結果を見て限定的に使い、D は #139 が片付いてから再評価する**（段階導入）。

1. **C（短期）**: Gate の `EventBuilder` に、伏字・切り詰めの直前で生値を走査する関数を 1 つ足す。結果は列挙型のラベルで送り、
   値そのものは送らない。サーバーには `web.masked_payload` を新しい検知器として足す（拡張点にファイルを追加するだけ）。
   これで「`token:` 前置で全回避」（#20）と「Cookie の中身が見えない」（#31）は、**少なくとも medium のアラートとして残る**。
   切り詰め（#21）は「上限の外にシグナルがあった」というラベル（`gate.signals_beyond_limit`）で表す。
2. **B（中期・限定的）**: C の誤検知率を良性コーパス（第 4 弾で CI 化済み）で測ったうえで、`secret_param` に限って値の形の条件を足す。
   ヘッダ名だけで決まる伏字（Cookie 等）には適用しない。パスワードの平文化を避けるためである。
3. **D（長期）**: #139 で Gate→サーバーの TLS 検証とポリシー署名が入り、運用文書で https を必須にできた時点で再評価する。
   それまでは採らない。

## 未確定・要検証

- C の形状検査で増える Gate のレイテンシ（p99）。#77 の測り方で計測する。
- C のシグナル名が攻撃者に知られた場合の回避（シグナルが付かない形に寄せる）。C は「消させない」ための補助で、署名検知の代わりではない。
- B の閾値（どの文字を含めば「秘密らしくない」とみなすか）は、実データがないため決め打ちになる。
